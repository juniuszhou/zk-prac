# Fiat Shamir Heuristic
如何避免verifier 选择数据，要求 prover提供证明。

但在实际区块链应用（比如以太坊上的智能合约验证 zkML 证明）或离线生成证明的场景中，交互是不现实的。

验证者（智能合约）是一个死板的代码，它不可能在证明者生成证明的过程中，突然跳出来抛出一个随机数，等证明者回应后再继续。

为了解决这个问题，现代密码学引入了一个大名鼎鼎的魔术：Fiat-Shamir 变换（Fiat-Shamir Heuristic）。通过这个变换，交互式协议可以被瞬间改造成“非交互式协议（Non-Interactive Proof）”。

下面我们来看看程序是如何在底层把这个“抛接球”的交互过程变成证明者“一个人单机完成”的。

1. 核心魔术：用“哈希函数”充当验证者在交互协议中，验证者唯一的武器就是“随机性”（随机挑选某一行让证明器打开）。只要这个随机数是公平、无法预测的，证明器就无法作弊。Fiat-Shamir 变换的核心思想是：用一个强抗碰撞的哈希函数，来代替活人验证者去摇号（产生随机数）。改造后的非交互式（单机）生成流程：证明者单机画死表格： 证明者在本地把几百万行的执行轨迹做成多项式，并构建好 Merkle 树。生成 Root： 得到一个 32 字节的根哈希 Root。“调教”哈希函数（获取挑战点）： 证明者不向任何人提问，而是直接把这个 Root 作为输入，塞进一个公开的哈希函数（例如 Keccak-256）：$$z = \text{Hash}(\text{Root})$$由于哈希函数的雪崩效应，只要 Root 有哪怕 1 bit 的改动，算出来的随机点 $z$（即要抽查的行号）就会发生翻天覆地的变化。证明者在交出 Root 之前，根本无法预测 $z$ 是多少。单机打包 Proof： 证明者根据算出来的 $z$，自己在本地把第 $z$ 行的数据以及对应的 Merkle 路径找出来，连同 Root 一起打包成一个最终的文件（Proof）。

2. 验证者（如智能合约）拿到 Proof 后怎么看？因为所有的规则和哈希函数都是公开的，验证者（Verifier）拿到这个单方生成的 Proof 文件后，只需要在本地复现这个过程：从 Proof 里读出 Root。验证者自己在本地运行一次一模一样的哈希计算：$z' = \text{Hash}(\text{Root})$。检查 Proof 里面包含的数据，是不是刚好就是第 $z'$ 行的 Merkle 路径和多项式求值。如果对得上，说明证明者在本地生成哈希路径时，完全没有偷看和作弊的可能。通过这种方式，原本需要来回倒手好几次的“多轮对话”，被压缩成了证明者单向发送一个 Proof 文件，验证者一次性闭眼读完即可的非交互式体验。

3. 在 zkML（可信推理）中的实际工程体现当你使用 RISC Zero、Succinct SP1 或 EZKL 运行大模型推理时，这个机制在代码库里被称为 Transcript（成绩单/上下文追踪器）：在 Prover 运行期间：底层的 Rust 代码（如 SP1Prover::prove）会创建一个 Transcript 对象。每当电路生成一个 Merkle Root 或者中间多项式，代码就会调用 transcript.append_message(root)。这个对象在内部会自动计算当前的连环哈希，并吐出伪随机数（挑战），自动作为下一步 FRI 协议的输入。

最终产物：最后吐出来的 Receipt（收据文件）是一个纯粹的二进制 Buff / JSON，里面已经包含了所有的多项式求值、Merkle 路径以及哈希链。总结理论上： 它的确需要交互（由多项式求值和 Merkle 打开的数学本质决定）。工程上： 通过 Fiat-Shamir 变换，证明者用“给 Root 算哈希”的操作代替了交互，将其变成了非交互式 SNARK / STARK。
